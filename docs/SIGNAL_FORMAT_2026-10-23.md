# SIGNAL_FORMAT — 定型信号と救援コードの送り方(形式だけ)

> 作成: 2026-10-23 / 状態: **案**(コードの一覧はこの文書では決めない。形式だけを決める)
> 範囲: サーバーが MQTT で受け取る定型信号と、送る救援コードの形。一覧(どの番号が何か)は別に決め、`共通仕様/01` に書く。
> 正は元の文書: `INTERFACES_2026-10-23.md`(JSON の形)、`FIELDS_2026-10-23.md`(項目)、`DATA_MODEL_2026-10-23.md`(表)。この文書は、そこに **数量 `n`** を足す差分と、一覧を作るための表の書き方をまとめたもの。食い違ったら共通仕様を先に直す。

## 0. 言葉

| 言葉 | 意味 |
|---|---|
| 定型信号 | 現場 → 本部。ボタンで送る決まった信号(SOS、無事、要救助者あり…)。項目名 `code`、1〜31 |
| 救援コード(指示コード) | 本部 → 現場。決まった指示(移動、集合、退避…)。項目名 `icode`、1〜255 |
| ポジション | 現場の場所に付けた番号(0〜255、0 は場所なし)。名前と場所は管理画面で変えられる |
| 数量 `n` | 人数などの数。**5 人きざみの区分で、最大 100**(§2) |

## 1. 定型信号の形(現場 → 本部)

トピック `reray/v1/up/{端末ID}/signal`、QoS 1、retain なし。

```json
{"v":1,"type":"signal","src":"dev-001","seq":42,"ts":1791849600,"code":5,"pos":3,"n":20,"via":"wifi"}
```

読み方: 「ポジション 3 から、要救助者 16〜20 人」(`code = 5` を「要救助者あり」とした場合)。

| 項目 | 必須 | 型・範囲 | 内容 |
|---|---|---|---|
| `v` | ◎ | 数値 | `1` |
| `type` | ◎ | 文字列 | `signal`(トピックの末尾と同じ) |
| `src` | ◎ | 文字列 | 端末ID(`dev-001`)。トピックの `{id}` と同じ |
| `seq` | ◎ | 0〜65535 | 端末ごとの連番 |
| `ts` | ○ | UNIX 秒 | 参考値。正はサーバーの受信時刻 |
| `code` | ◎ | 1〜31 | 定型信号のコード。**1 は SOS で固定** |
| `pos` | △ | 0〜255 | 今いるポジション。無ければ 0 |
| `n` | △ | 5, 10, 15 … 100 | 数量(区分の上限人数)。**数を使わない信号では項目ごと省く** |
| `via` | ○ | `wifi` / `lora` | 届いた経路 |

## 2. 数量 `n` の決まり

| 決まり | 内容 |
|---|---|
| 区分 | **5 人きざみ、最大 100 人。** 5 の倍数で 5〜100 の 20 通り |
| 値の意味 | **区分の上限**を入れる。`n = 5` は「1〜5 人」、`n = 20` は「16〜20 人」、`n = 100` は「96〜100 人」 |
| 表示 | 「(n−4)〜n 人」に直す。画面と、グラスの文で同じ規則 |
| 上限 | 最大の区分は「96〜100 人」。101 人以上は送れない |
| 何の数か | **`code` ごとに決める**(人数、食数など)。`n` 自身には単位がない |
| 省略 | 数を使わない信号では送らない。`n = 0` は使わない |
| 範囲外が届いたとき | 5 の倍数でない値や 100 超は、サーバーが**そのまま保存**する(捨てない)。画面は届いた値のまま出し、「区分外」の印を付ける |
| LoRa での運び方 | 区分の番号(`n ÷ 5` = 1〜20)を 5 ビットで運ぶ。名前や文は LoRa に載らない |

数を `code` に埋め込む案(「1 人」「2 人」を別のコードにする)は、1〜31 の枠を使い切るので採らない。

## 3. 救援コードの形(本部 → 現場)

トピック `reray/v1/down/{端末ID}/text`(一斉は `down/all/text`)、QoS 1、retain なし。自由な文と同じ `text` の形に、項目を足す。

```json
{"v":1,"type":"text","src":"pc","dst":"dev-001","seq":8,"mid":13,"ts":1791849700,"icode":1,"pos":3,"body":"北口へ移動"}
```

| 項目 | 内容 |
|---|---|
| `icode` | 救援コード。あるときだけ付く |
| `pos` | ポジション番号(`icode` とセット。0 は場所なし) |
| `body` | 文に直したもの。**Wi-Fi の端末はそのまま表示**。**LoRa では運ばず**、端末が `icode` と `pos` から文を作る |
| `mid` | サーバーが先に DB に保存して得た番号。確認(ack)がこの番号で戻る |

LoRa の下りに載るのは数字だけ: 定型信号は `code` と `pos`(と区分番号)、救援コードは `icode` と `pos`。

救援コードにも数量を付けるか(例:「5 人派遣」)は**未決**(§6)。付ける場合は、同じ規則の `n` を足す。

## 4. 一覧の書き方(これを埋める。`共通仕様/01` に置く)

一度決めた番号は変えない(変えると過去の記録の意味が変わる)。

### 定型信号(現場 → 本部)

```markdown
| code | 名前 | ボタン操作 | グラスに出す文(送った本人向け) | 本部の画面の短い名前 | ポジションを添える | 数を使うか | 数の意味 | 端末で選べる区分 | 優先度 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | SOS | 長押し | SOS を送りました | SOS | 任意 | なし | — | — | 最高 |
| 5 | 要救助者あり | | | 要救助 | 必須 | 必須 | 人数 | 5, 10, 20, 50, 100 | 高 |
```

| 列 | 決まり |
|---|---|
| `code` | 1〜31 の整数。**1 は SOS 固定**(サーバーの SOS 表示と並び順が使う) |
| ポジションを添える | 必須 / 任意 / 添えない。添えない信号は `pos = 0` |
| 数を使うか | 必須 / 任意 / なし |
| 数の意味 | 1 語(人数、食数…) |
| 端末で選べる区分 | 20 通り(5〜100)のうち、端末のボタンで選べる値。順に切り替えるので、よく使う値だけを並べる。通信の形は変わらない |
| 優先度 | 最高 / 高 / 通常。LoRa が混んでいるときの送る順に使う |

### 救援コード(本部 → 現場)

```markdown
| code | 名前 | ポジションを使うか | 文の作り方(ポジションあり) | 文の作り方(ポジションなし) | 確認を要求 |
|---|---|---|---|---|---|
| 1 | 移動 | 使う | {ポジション名}へ移動 | (使わない) | 要 |
| 2 | 待機 | 使わない | — | その場で待機 | 不要 |
```

- 文は「ポジション名 + `text`」で作る(サーバーの `instruction_codes` は番号と `text` の 2 列)。ポジションなしの文は別に要る(「へ移動」だけでは文にならない)。
- 名前や文は、端末が持つ表で作る。文を変えたいときは、番号は変えずに表を差し替える。
- 表に無い番号を受け取っても、サーバーは数値のまま保存し、画面は番号のまま出す。
- 定型信号の数は、現場で選べる数で考える(「選ぶ」ボタンを何回も押す)。5〜8 個が現実的で、31 個は上限であって目標ではない。

## 5. 各パートで変わること

| 場所 | 変更(案) |
|---|---|
| サーバー DB `signals` | `n`(`TINYINT UNSIGNED`、空可)を 1 列足す |
| サーバー API(端末一覧の `last_signal`、`/api/logs`) | `n` を足す。表示の文は画面側で作る |
| サーバーの検証 | `n` が区分外でも捨てない(§2)。それ以外は既存の規則のまま |
| 端末(ハード)の LoRa フレーム | 今の報告フレームは、4 ビットの区分を 4 つ(人数、負傷者、要救助、必要物資)持つ。1 信号に数が 1 つなら、そのうち 1 つを「区分番号(1〜20)」に置き換えれば収まる。変更はハード担当と合わせる |
| 管理画面 | `n` を「(n−4)〜n 人」に直して出す。「区分外」の印も出す |
| 共通仕様 | 02(signal に `n`)と 01(一覧の表の列)に反映が必要 |

## 6. 決まっていないこと

| # | 内容 | 今の扱い |
|---|---|---|
| 1 | 救援コード(本部 → 現場)にも数量 `n` を付けるか | 未決。必要なら同じ規則で足す |
| 2 | ポジションなし(`pos = 0`)の救援コードを許すか | 未決。許すなら文が 2 通り要る |
| 3 | 救援コードに「確認を要求」を付けるか | 未決。付けるなら、返事の無い端末を画面で目立たせる機能が要る(v1 は「端末に届いた」までの方針) |

## 7. サーバー担当の注記(2026-10-23)

この文書を `docs/` に入れるときに見つけた食い違い。直すかどうかは書いた人・ハード担当と相談する。

| # | 場所 | 食い違い | 案 |
|---|---|---|---|
| 1 | §2「LoRa での運び方」と §5「端末の LoRa フレーム」 | §2 は区分番号(1〜20)を **5 ビット**で運ぶ。§5 は今の **4 ビット**の欄の1つに置き換えれば収まるとしている。4 ビットは 0〜15 の 16 通りなので、**20 通りは入らない** | 欄を 5 ビットに広げる(フレームが 1 ビット増える)か、区分を 16 通り以下にする(例:5 きざみで 80 人まで)。ハード担当と決める |
| 2 | §2「範囲外が届いたとき」と §5「`n` は `TINYINT UNSIGNED`」 | 「そのまま保存する」とあるが、`TINYINT UNSIGNED` に入るのは 0〜255 の整数だけ。256 以上・負の数・小数・文字列は保存できない | 0〜255 の整数なら `signals.n` にそのまま保存(区分外の印は画面で付ける)。それ以外は `signals` に入れず、`events` に原本だけ残す(`result = invalid`、`note = n out of range`)。サーバーの暫定の扱いとして `FIELDS` に書いた |
| 3 | §3 の例の `body` | `"北口へ移動"`。`INTERFACES` §2.1 の例は `"ポジション3(北口)へ移動"` | 端末の画面の幅しだいなので、文の作り方は一覧(§4)で決める。それまでは短い方(`北口へ移動`)に合わせる |
