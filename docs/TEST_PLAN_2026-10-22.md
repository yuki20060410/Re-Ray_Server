## M1:上りの最小経路(疑似端末 → ブローカー → サーバー → 保存)

- [ ] `mosquitto -c config/mosquitto.conf -v` で起動できる
- [ ] サーバーアプリが `reray/v1/up/#` を購読できる(永続セッション)
- [ ] 疑似端末の signal が `signals` に保存される(`received_at` つき)
- [ ] 登録していない端末の signal も保存され、`registered = 0` の端末が作られる
- [ ] 不正な JSON(壊れた、`v=2`、`src` 不一致)を送っても、サーバーが落ちず、events に `invalid` として残る
- [ ] サーバーを止めている間に publish した QoS1 の signal が、再起動後に保存される

**合格(案)**:疑似端末の 100 件が、欠けも重複もなく保存される。再起動をはさんでも 100 件そろう。

## M2:端末の状態・記録(API)

**端末の登録と一覧**

- [ ] `POST /api/devices` で登録でき、`PUT /api/devices/{id}` で持ち主の名前を変えられる
- [ ] `GET /api/devices` が `owner` / `online` / `via` / `battery` / `glass` / `last_signal` を返す(チーム案の形)
- [ ] status で `battery` と `glass` が更新される
- [ ] `battery` が無い status で、既存の値を消さずに扱える(空にするか前の値のままか、ここで決めて記録)

**online の判定**【修正案】

- [ ] 何か届くと `online = true`、`last_seen_at` が更新される
- [ ] 遺言(`online: false`)で `online = false` になる
- [ ] Wi-Fi の端末から 90 秒何も来ないと `online = false` になる
- [ ] `via = lora` の端末から 15 分何も来ないと `online = false` になる(待つ間は true のまま)

**記録**

- [ ] `GET /api/logs` を、端末・種類・日付で絞り込める
- [ ] CSV を出力でき、Excel で文字化けせずに開ける【追加案】

**合格(案)**:5 端末の疑似データで、API の値が手計算と一致する。online の切り替わりが、上の時間(±数秒)で起きる。

## M3:文字の送信と届き具合

**送信**

- [ ] `POST /api/messages` で、個別(`dst` = 端末ID)と一斉(`dst` = `all`)を送れる。返る `id` が messages.id である
- [ ] **DB に保存してから** MQTT に流れる(順序をログで確認)
- [ ] 個別は `down/{id}/text`、一斉は `down/all/text` に流れる。`mid` が付く【修正案】
- [ ] 本文が上限(全角40文字【案】)を超えたら 422。登録されていない端末ID も 422
- [ ] ブローカーに接続できないとき、503 を返し、messages に `failed` が残る

**届き具合**

- [ ] 疑似端末が ack(`ack_mid`)を返すと、acks に入り、`GET /api/messages/{id}` の数が増える
- [ ] 同じ端末から同じ ack が 2 回来ても 1 行のまま(最初の時刻)
- [ ] 分母が、**送った時に Wi-Fi だった端末**になる。LoRa 状態の端末は別に数える(例 `5台中4台`、`LoRa中: 1台`)【修正案】
- [ ] 送ったあとで端末の状態が変わっても、分母が変わらない(message_targets)
- [ ] LoRa 状態の端末があとで Wi-Fi に戻って ack を返すと、`acked_at` が入る(分母は変わらない)
- [ ] `ack_mid` が無く `ack_src` / `ack_seq` だけの ack で、暫定の対応づけが動く。曖昧なら対応づけず events に残る(合意前の暫定)

**合格(案)**:個別・一斉でそれぞれ 10 回ずつ、送信〜届き具合の集計が成功する。

## M4:異常系(疑似端末で再現)

| 項目 | 手順 | 期待 |
|---|---|---|
| 重複 | 同じ `src` と `seq` の signal を 3 回送る | 保存は 1 件。events に `duplicate` が 2 件 |
| 二重の経路 | 同じ `src` と `seq` を `via=wifi` と `via=lora` の両方で送る | 先に届いた方だけ残り、`via` もその方 |
| 窓の外 | 同じ `src` と `seq` を 10 分以上あけて送る | 別の signal として保存(seq が一周した想定) |
| seq の回り込み | seq を 65534 → 65535 → 0 → 1 と送る | 4 件とも保存(重複にならない) |
| 欠番 | seq 10 のあとに 14 を送る | 両方保存。エラーにしない |
| 遅延到着 | 回線断を模擬して溜め、一定時間後にまとめて送る | 保存順が前後しても、受信時刻で最新が決まる。`ts` との差が分かる |
| 切れる端末 | 遺言つきで接続した疑似端末を突然切る | `online = false` |
| 黙る端末 | Wi-Fi の端末が status を / LoRa の端末が心拍を送らなくなる | 90秒 / 15分で `online = false` |
| 戻る端末 | 切れた端末が signal / status を再び送る | `online = true` に戻る |
| 不正な入力 | 壊れた JSON、`v=2`、`src` 不一致、`dev-000`、`dev-65535` | すべて `invalid`。サーバーは止まらない |
| 大きすぎる本文 | 4 KB 超の本文 | `invalid`。サーバーは止まらない |
| 未知の項目 | `x` など知らない項目つきの signal | 受理する。原本に残る |
| ブローカー断 | ブローカーを止めて再開する | 自動で再接続し、購読を再開する |
| サーバー再起動 | サーバーを止め、その間に signal を送って再起動 | 取りこぼさない。再起動直後に端末が一斉に「切れた」にならない |
| 同時の文字 | 3 件の text を続けて送り、別々の端末が ack を返す | ack が正しい text に対応づけられる(`ack_mid`) |

**合格(案)**:すべての行が期待どおり。サーバーが一度も落ちない。
「直近10分」「90秒」「15分」の値は仮置き。ここで見直して、定数を直す。

## M5:実機結合(ハード側 S5 と同時に実施)

> [!IMPORTANT]
> **前提:ハード側の S0(規制の確認)が完了し、出口と端末が用意されていること。** サーバー側は電波を出さないが、実機の試験はハード側の手順と規制の確認に従う。

**受信**

- [ ] 出口の端末が MQTT に接続し、実際の signal(`via = lora`)がサーバーに保存される
- [ ] Wi-Fi の端末の signal(`via = wifi`)も保存される
- [ ] 上り:端末のボタンで送った定型信号が、`GET /api/devices` の `last_signal` に出る(10 回)

**下り**

- [ ] 画面から送った文字が、Wi-Fi の端末で受信される(10 回)
- [ ] ack が集まり、「N台中M台に届いた」が正しく出る
- [ ] 【修正案】Wi-Fi を切った端末に text を送り、Wi-Fi に戻ったあとで text が届き、ack が戻る

**回線断**

- [ ] 出口の回線を切り、LoRa 状態の端末から signal を数件送る。復旧後に、遅れて届いた分が重複・順序の乱れなく保存される

**実機で記録すること**

- [ ] status の本文(特に LoRa 状態の端末の心拍の形)。`INTERFACES_2026-10-23.md` §2.3 に項目を追記する
- [ ] `ts` と受信時刻の差、`ts` が 0 や欠けるときの様子
- [ ] 端末の seq が再起動で 0 に戻るか。【修正案】の乱数の始まりが実装されているか

**合格(案)**:上り・下りが 10 回ずつ成功し、回線断→復旧で溜まった分が正しく表示される(ハード側 S5 の合格基準と同じ)。
