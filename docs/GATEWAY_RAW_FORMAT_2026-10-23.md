# GATEWAY_RAW_FORMAT — LoRa 由来の連絡を、サーバーが分解する(サーバー側の実装メモ)

> 作成: 2026-10-23(方角 `dir` を反映して更新) / 更新: 2026-11-06(リポジトリに追加。§6 にサーバー担当の注記を足した) / 状態: **案**(方針は決定・合意待ち。形式の細部はハード担当と合意してから確定)
> **約束ごと(トピック・包みの形・フレームの形)は `共通仕様/00_統合案_2026-10-23.md` が正**(C-14・C-16・C-18・C-21)。この文書は、そのうち**サーバーが実装すること**だけを書く。
> 決めたこと(2026-10-23): **Wi-Fi の端末は JSON のまま。LoRa で届いたものだけ、出口が受け取ったバイト列をそのまま MQTT に載せ、サーバーが分解する(案 C)。**
> 表の名前は `DATA_MODEL_2026-10-23.md`(`events`・`acks`)で書いている。すみださんのテーブル定義案(`lora_frames`・`message_deliveries`)に寄せるかは `DB案の比較_2026-11-06.md` の DB-015。

## 0. なぜこうするか

| 理由 | 内容 |
|---|---|
| 圧縮は意味がない | JSON(101 B)を gzip しても 106 B。縮むのはバイナリにしたときだけ(MQTT 1 通で 133 B → 49 B) |
| LoRa はすでにバイナリ | 区間で一番細い LoRa は、報告フレーム 17 バイトで運んでいる |
| 署名をサーバーで確かめられる | 今の設計は「出口が信じたものを信じる」。生のバイト列なら、サーバーが HMAC の先頭 4 バイトを検証できる |
| 証拠が残る | 受け取ったバイト列そのものと RSSI/SNR を記録できる |
| 出口が簡単になる | 出口は JSON に直す処理が要らない |
| Wi-Fi 側は今のまま | `mosquitto_pub/sub` で読めて、疑似端末も作りやすい |

## 1. サーバーが受け取るもの

トピック `reray/v1/up/gw/{出口ID}/lora`(QoS 1)。中身は `fmt`(1 B)+ `rssi`(2 B)+ `snr`(1 B)+ `age_ms`(4 B)+ LoRa のフレーム(14〜19 B)のバイナリ(詳しくは共通仕様 §4.4)。

- `received_at` は「サーバーの受信時刻 − `age_ms`」(溜めて送られた分も、出口が実際に受けた順に並ぶ)。**DB の既定値(今の時刻)に任せず、サーバーが値を渡す。**
- サーバーが購読している `reray/v1/up/#` に含まれる。追加の購読は要らない。
- これまでの検証規則「`src` がトピックの `{id}` と一致」「バイナリは捨てる」は、**このトピックだけ例外**。

## 2. サーバーが分解して、今の項目に直す

| フレームの項目 | → 今の項目 |
|---|---|
| `src`(16 ビット) | `src` = `dev-NNN`(NNN は 3 桁以上。0 と 65535 は不正) |
| `seq` | `seq` |
| REPORT:`flags` の上位 5 ビット(bit 3〜7) | `code`(定型信号) |
| SOS(種類 1) | `code = 1` |
| REPORT/SOS:位置の 1 バイト(5 バイト目) | `pos` |
| REPORT/SOS:数量の区分番号(6 バイト目。1〜20、0 は無し) | `n` = 区分番号 × 5(無しなら項目なし) |
| REPORT/SOS:方角(7 バイト目の下位 4 ビット。1〜8、0 は無し) | `dir`(無しなら項目なし。1〜8 以外はそのまま保存して「範囲外」の印) |
| REPORT/SOS:`time`(UNIX 秒、0 = 未同期) | `device_ts`(0 なら空) |
| (トピックから) | `via = lora` |
| ACK(種類 3、`ack_kind = 3`):`ref_src`、`ref_seq` | 指示への確認。`ref_seq`(= `pc` の連番)から `messages.id`(mid)を引いて `acks` に記録 |
| ACK(`ack_kind = 1, 2`)、BEACON | LoRa の中だけのもの。`events` に `ignored` として残すだけ |
| INSTRUCT(種類 2) | 下りのフレーム。上りに来たら不正(`invalid`) |

`pc` の連番から mid を引くとき、連番は 65535 で 0 に戻るので、**直近(例 10 分)の messages で連番が一致する、最新の 1 件**を使う。曖昧なら対応づけず `unmatched` で残す(既存の暫定規則と同じ)。

## 3. 処理の順番

1. `events` に原本を書く(`payload` は 16 進文字列、`note` に `rssi / snr / age_ms / 出口ID`)
2. 長さ、版、種類を確かめる → だめなら `invalid`
3. 署名を確かめる → 合わなければ `invalid`(`note = bad mic`)。サーバーは止まらない
4. 種類に応じて §2 の項目に直し、**以降は Wi-Fi の端末の signal と同じ処理**(重複判定 → `signals` に保存 → `devices` 更新 → 画面へ)
5. 重複の判定は今までどおり(直近 10 分の `src` + `seq`)。LoRa の中継で同じフレームが複数の出口から届いても、1 件になる
6. signal を保存したら、これまでどおり `reray/v1/down/{src}/ack`(本部に届いた)を返す。**LoRa の端末向けには、出口がこれを LoRa の ACK に直して流す**(共通仕様 §6.3)。サーバーは LoRa を意識しない

署名の鍵は `.env`(例 `RERAY_HMAC_KEY`)から読む。git に入れない。署名の 4 バイトは短く、**誤受信や単純ななりすましを防ぐ最小限の仕組みで、本格的な認証ではない**。

## 5. ハード側に頼むこと(共通仕様 §6.3 と合わせて)

1. 出口は LoRa のフレームを**変換せず**、共通仕様 §4.4 の包みにして上のトピックへ publish する(出口の JSON 変換は、LoRa 由来の分には使わなくなる)。
2. **署名つきのテスト用データ**(鍵、フレーム、正しい分解の結果のセット)を渡す。サーバーの実装がハードの実装と同じ結果になることを確かめるため。方角を使う信号(`dir`)と、数量を使う信号(`n`)の両方を含める。
3. REPORT/SOS に**数量の欄**(6 バイト目、区分番号 1〜20)と**方角の欄**(7 バイト目の下位 4 ビット、1〜8)を作る。今の報告フレームは 4 ビットの区分を 4 つ持つ。
4. 出口は `reray/v1/down/#` を購読し、**指示コードの text を INSTRUCT に、`down/{id}/ack` を LoRa の ACK(種類 2)に直して流す**。「本部に届いた」の出どころはサーバー 1 か所になる(出口が自分で publish 成功を見て返す案はやめる)。

### サーバー担当の注記(2026-11-06)

10/23 にサーバー側で出した LoRa の論点(`n` のビット数、下りの経路、LoRa からの「届いた」)は、共通仕様の統合案(C-16・C-18・§6.2)でほぼ決まった。決まっていない分だけ、ここに残す。

| # | 内容 | 案 |
|---|---|---|
| 6 | **本部の連番 `pc` の一周**。LoRa の返事(ACK 種類 3)は `ref_seq`(= `pc` の連番)で指示を指す。一方、「本部に届いた」(`down/{id}/ack`)も同じ `pc` の連番を使う(`DATAFLOW` §8.4)ので、signal が届くたびに連番が 1 つ進む。16 ビットなら 10 分で一周することはまず無いが、**8 ビット(DB 修正依頼 DB-002)だと簡単に一周し、取り違える** | 「本部に届いた」には `pc` の連番を使わない(別の連番にするか、`seq` を 0 固定にする)。text と INSTRUCT だけが `pc` の連番を進めるようにする |
| 7 | **「本部に届いた」を LoRa に流す範囲**。統合案 §6.3 では、出口が `down/{id}/ack` を全部 LoRa に放送する。Wi-Fi の端末への ack や、ほかの出口が中継した分まで流れ、920MHz 帯の送信時間を使う | 出口は、**自分が中継した `(src, seq)` に合う ack だけ**を LoRa に流す。出口は中継した組を少し(10 分ぶん)覚えておく |
| 8 | **SOS の送り直し**。統合案 §6.2 は「最大 3 回で止め、『未達』を表示」。`01_要件定義` の FA-03 は「SOS は届くまで送り直す」 | どちらにするかチームで決める。SOS だけ回数の上限を外すなら、待ちを延ばしていき、ある長さからは延ばさずに送り続ける(例:5 → 10 → 20 → 40 → 60 秒、以後 60 秒ごと)。送信時間の予算を超えないことが条件 |
| 9 | **Wi-Fi の端末の「本部に届いた」**。端末はブローカーの受け取り(PUBACK)を「本部に届いた」と見なさない | 端末は `down/{自分のid}/ack` の `ack_seq` だけで照合する。同じ ack が 2 回来ても(QoS 1 の再配信、Wi-Fi と LoRa の両方で届いた signal)、2 回目は捨てるだけ。共通仕様 02 に一文足す |
