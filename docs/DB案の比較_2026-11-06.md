## 1. 先に決めないと進めない3点

| # | 項目 | A（リポジトリ） | B（すみだ案） | 影響 |
|---|---|---|---|---|
| 1 | **時刻の時間帯** | **UTC** で保存。API で +09:00 に直す。`compose.yaml` が `--default-time-zone=+00:00` で起動する | **日本時間**（`time_zone = '+09:00'`） | ⚠ **いちばん危ない**。【追記】B の `SET time_zone = '+09:00'` が効くのは、CREATE 文を流した**その接続だけ**。サーバーや Web がつなぐ接続は compose の `+00:00` になるので、`DEFAULT CURRENT_TIMESTAMP` や `NOW()` で入る値は UTC になる。本当に危ないのは、**つなぐ側ごとに時間帯がばらばら**になること（例：Web だけが `+09:00` でつなぐと、同じ表に UTC と日本時間が混ざる）。重複判定の「直近10分」は同じ接続の時計どうしで比べるので動き、ずれに気づきにくい |
| 2 | **端末IDの型** | `VARCHAR(16)` に `dev-001` のまま | `SMALLINT UNSIGNED` の数値（1 = dev-001）。出入り口で付け外し | API・MQTT処理・全表の外部キーに関わる。数値の方が LoRa の16ビットとそのまま合い、索引も小さい |
| 3 | **決まった値の持ち方** | `VARCHAR` ＋サーバーのコードで確かめる（値を足すたびに表を変えたくない） | `ENUM` で DB が確かめる | `via`・`kind`・`response` など。B だと `ALTER TABLE` が増える |

> 細かいが揃えたいもの: MySQL の版（A: **8.4**（compose）／B: 8.0）、主キーの型（A: `INT`／B: `BIGINT`）。

## 3. 列・決まりの違い

### signals

| 項目 | A | B |
|---|---|---|
| ポジションなし | `pos = 0` | `position_id = NULL` |
| ポジションの外部キー | **付けない**（ポジションを消しても過去の番号を残すため） | **付ける**（positions の行を消せなくなる。【追記】それより、**表に無い番号の信号が書けずに落ちる**。下の ⚠） |
| 定型信号のコードの外部キー | **付けない**（一覧に無い番号も保存する） | **付ける**（`signal_codes`）。【追記】下の ⚠ |
| 数量 | `n` | `quantity` |
| 方角 | `dir`（2026-11-06 に追加） | `direction` |
| 区分外・範囲外の印 | なし（画面で判定） | `is_out_of_range` |
| LoRa の元データ | なし（events に残す） | `lora_frame_id` |
| SOS の対応済み | なし（最新が SOS でなくなるまで、と未決） | `handled_at` |
| 受け取った時刻 | サーバーが渡す | `DEFAULT CURRENT_TIMESTAMP(3)`。【追記】LoRa 由来は「受信時刻 − `age_ms`」（GATEWAY_RAW_FORMAT §1）なので、既定値に任せず、サーバーが渡す必要がある |

> ⚠ 【追記】**外部キーで信号が落ちる**（B の 2 か所）
> - `signals.code → signal_codes`: 一覧の INSERT（DB-003）が入るまでは、`signal_codes` が空。この間は **SOS（code = 1）すら書けない**。一覧が入ったあとも、端末が新しい番号を先に使うと落ちる。共通仕様の「未定義のコードも保存する」（INTERFACES §2.5、SIGNAL_FORMAT §4）に反する。
> - `signals.position_id → positions`、`devices.position_id → positions`: 管理画面でまだ名前を付けていないポジション番号を端末が送ると、信号が書けない。ポジションは「番号は端末、名前は本部で後から付ける」（10/20 の決定）なので、表に無い番号が届くのは普通のこと。
> - どちらも、**信号の表からは外部キーを外す**。名前は画面で LEFT JOIN して引き、表に無ければ番号のまま出す。

### messages

| 項目 | A | B |
|---|---|---|
| 種類 | `kind` = `free` / `order` ＋ `source` = `web` / `transcript` | `kind` = `text` / `instruction` / `transcript` |
| 一斉送信 | `dst = 'all'` | `dst_device_id = NULL` |
| 本文の長さ | `VARCHAR(255)` | `VARCHAR(40)`（グラスの文字数待ち） |
| 流せたか | `publish_state`（sent / failed） | なし |

### 確認（ack）

| 項目 | A | B |
|---|---|---|
| 記録するもの | 「届いた」だけ（`acked_at`） | 「受け取った」＋「了解／できない」 |
| 送った時の経路 | `message_targets.via_at_send`（wifi / lora） | `via_at_send`（wifi / lora / **offline**） |

> ⚠ `SIGNAL_FORMAT` §6-3 は「確認を要求するかは未決、v1 は**端末に届いた**まで」。B の「了解／できない」は、その決定より先に進んでいる。ハードの `MESSAGE_SPEC` も ack_kind は 1〜3（近傍・サーバー到達・指示受領）までで、4・5 はまだ無い。

> ⚠ 【追記】**本部の連番の一周**。LoRa の返事（ACK 種類 3）は `ref_seq`（= 本部の連番）で指示を指し、B は `idx_messages_seq` で mid を引く。ところが「本部に届いた」（`down/{id}/ack`）も**同じ本部の連番を使う**（DATAFLOW §8.4）ので、信号が届くたびに連番が 1 つ進む。DB-011 の「8 ビットだと一周する」心配は、文字起こしだけでなく、この分でも大きくなる。「本部に届いた」には本部の連番を使わない案を GATEWAY_RAW_FORMAT §6 #6 に書いた。

### devices

| 項目 | A | B |
|---|---|---|
| 未登録の端末 | 自動で登録し `registered = 0` で区別 | 自動で登録（区別する列なし。製品では見直し） |
| 最新の信号 | 問い合わせで出す | `last_signal_id` に持つ |
| 今のポジション | `pos` | `position_id` |

### 重複の判定

- 両方「直近10分の同じ端末＋seq」をサーバーのコードで判定、一意制約なし → **一致**
- B は端末の行に `FOR UPDATE` をかけてから判定（Wi-Fi と LoRa の同時到着で2件になるのを防ぐ）。**A には無い。B の手順を取り入れるべき**
- ⚠ 【追記】ただし B の手順は、**端末の行がまだ無いと鍵がかからない**（`SELECT … FOR UPDATE` が 0 行）。未登録の端末から同じ信号が同時に 2 つ来ると、両方が `devices` に INSERT しようとして片方が主キーの重複で失敗し、その信号が落ちる。先に行を作ってから鍵をかける:

```sql
START TRANSACTION;
INSERT INTO devices (id) VALUES (?) ON DUPLICATE KEY UPDATE id = id;  -- 無ければ作る（あれば何もしない）
SELECT id FROM devices WHERE id = ? FOR UPDATE;                      -- ここで必ず1行に鍵がかかる
-- 以降は B §7 と同じ（重複の判定 → INSERT signals → UPDATE devices）
COMMIT;
```

## 5. まとめ方の提案

**土台**

| 項目 | おすすめ | 理由 |
|---|---|---|
| 時刻 | **UTC で保存**（A） | compose がすでに UTC。API で +09:00 にするだけで済み、サーバーの置き場所が変わっても困らない。【追記】あわせて「**どの接続も `time_zone = '+00:00'` でつなぐ**」を決まりにする（サーバー・Web・手で SQL を流す人の全員） |
| 端末ID | **数値**（B） | LoRa の16ビットと同じ。ただし API・MQTT の出入り口で `dev-001` に直す関数を1か所に作る |
| 決まった値 | **VARCHAR ＋コード**（A） | 種類はまだ増える（`offline` が後から出てきたように） |

**表**（B を軸にして）

- `message_targets` ＋ `acks` → **`message_deliveries` 1表**にする。ただし `response` 列は「確認を要求するか」が決まるまで空のまま
- 原本は **`events`（全部）と `lora_frames`（LoRa の生データ）を両方**持つ。`events` は Wi-Fi の JSON や下りの記録、遺言にも要る。`lora_frames` は署名検証と rssi の調査に要る
- `signals` の **ポジションとコードに外部キーは付けない**（A の理由が正しい。【追記】付けると信号が落ちる）。0 は NULL にする（B）でよい
- **`FOR UPDATE` の手順**（B）を、【追記】**先に行を作る形**（§3 重複の判定）で入れる。**`publish_state`**（A）、**`registered`**（A）も入れる
- 【追記】`signals.received_at` は既定値に頼らず、サーバーが渡す（LoRa 由来の `age_ms` を引くため）
- `transcripts` は作らず、`messages.kind='transcript'` で足りる（A 自身が「要らないかも」と書いている）
