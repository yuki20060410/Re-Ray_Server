## 1. MQTT:トピックと QoS

`{id}` は端末ID(例 `dev-001`)。

| トピック | サーバーの動き |
|---|---|
| `up/{id}/signal` | 購読。保存 |
| `up/{id}/status` | 購読。端末の状態を更新 |
| `up/{id}/ack` | 購読。どの text への確認かを記録 |
| `down/{id}/text`、`down/all/text` | publish |
| `down/{id}/ack` | 【案】publish。signal を保存したら返す(§2.6) |

(トピックは `reray/v1/` が先頭に付く。)

- `up` は端末から上がるもの、`down` は端末へ下ろすもの。`v1` は形式のバージョン(形式を壊す変更をしたら `v2`)。
- 出口が LoRa で受けた分は、出口が端末に代わって `up/{その端末のid}/...` に流す(`via` は `lora`)。
- **サーバーは `reray/v1/up/#` を購読する**(共通仕様 03)。

### 接続の設定

| 対象 | 設定 |
|---|---|
| サーバーアプリ | クライアントID は固定(例 `reray-server`)。永続セッション(clean session なし)で、再起動中の QoS1 を取りこぼさない。切れたら自動で再接続 |
| 端末 | 【修正案】`clean session = false`、クライアントID = 端末ID。Wi-Fi が切れている間の text をブローカーが溜め、戻ったときに渡す。**端末側の設定で、サーバーは関与しない** |
| ブローカー | `config/mosquitto.conf`(検証用、匿名、ローカル LAN、永続化あり) |

### 端末が落ちたことの検知(遺言)

端末は接続するとき、遺言(Last Will)を `reray/v1/up/{id}/status` に登録する。黙って切れると、ブローカーが代わりに次を流す。

```json
{"v":1,"type":"status","src":"dev-001","online":false}
```

サーバーはこれで、その端末を「切れた」にする(`ARCHITECTURE_2026-10-22.md` §5)。遺言には `seq` と `ts` がない。

## 2. MQTT:JSON の形

共通の項目:

| 項目 | 内容 |
|---|---|
| `v` | 形式のバージョン。今は `1` |
| `type` | `text` / `signal` / `status` / `ack` |
| `src` | 送信元。端末ID か `pc` |
| `seq` | 送信元ごとの連番(u16) |
| `ts` | 送った時刻(UNIX 秒) |

文字コードは UTF-8。

### 2.1 text(下り:管理PC → 端末)

```json
{"v":1,"type":"text","src":"pc","dst":"all","seq":7,"ts":1791849600,"body":"北口に集合してください"}
```

【修正案】`mid`(messages.id)を足す:

```json
{"v":1,"type":"text","src":"pc","dst":"all","seq":7,"mid":12,"ts":1791849600,"body":"北口に集合してください"}
```

| 項目 | 内容 | サーバーの扱い |
|---|---|---|
| `dst` | 宛先。端末ID か `all`(一斉) | 個別は `down/{id}/text`、一斉は `down/all/text` に出す |
| `body` | 本文。上限は全角40文字【案】 | 上限は**定数1つ**にして API でも断る【修正案】。グラスが決まったらこの定数だけ変える |
| `seq` | `pc` の連番 | サーバーが採番 |
| `mid` | messages.id【修正案】 | **先に DB に保存して id を得てから** MQTT に流す |

#### 指示コードの形【案】(10/20 の決定:LoRa でも下ろす)

本部 → 現場の下りは2種類になる。

| 種類 | いつ届くか | 中身 |
|---|---|---|
| 自由な文 | Wi-Fi のときだけ | `body` |
| 指示コード+ポジション | Wi-Fi でも LoRa でも | `icode` と `pos`。`body` にも文に直したものを入れる |

```json
{"v":1,"type":"text","src":"pc","dst":"dev-001","seq":8,"mid":13,"ts":1791849700,"icode":1,"pos":3,"body":"ポジション3(北口)へ移動"}
```

| 項目 | 内容 | サーバーの扱い |
|---|---|---|
| `icode` | 指示コード(§2.5、指示コード表) | 指示コードの形のときだけ付ける |
| `pos` | ポジション番号 | 指示コードの形のときだけ付ける。0 は「場所なし」 |
| `body` | 文に直したもの | Wi-Fi の端末はそのまま出せばよい。**LoRa では運ばない**(端末側で `icode` と `pos` から文を作る) |

- `type` を `text` のまま、項目を足す形にした(端末は `icode` の有無で見分ける)。別の `type` にするかは要合意(§8)。
- LoRa 状態の端末へどう下ろすか(出口がどのトピックを購読し、LoRa のパケットに直すか)は未決(§8)。

### 2.2 signal(上り:定型信号)

```json
{"v":1,"type":"signal","src":"dev-001","seq":42,"ts":1791849600,"code":2,"pos":3,"via":"wifi"}
```

| 項目 | 内容 | サーバーの扱い |
|---|---|---|
| `code` | 定型信号のコード(§2.5) | 保存・表示 |
| `pos` | 【案】ポジション番号(10/20 の決定:定型信号に添える)。0 は「場所なし」 | 保存。端末の「今のポジション」にも使う。無くても受け付ける(0 扱い) |
| `via` | 届いた経路。`wifi` か `lora` | 保存。端末の「経路」の表示に使う |
| `ts` | 端末が付けた時刻 | **参考値**。サーバーの受信時刻(`received_at`)を正とする |

任意の追加項目 `x`(区域・人数区分・RSSI など)を出す案がハード試作にある(§7)。**チーム仕様にはない。** サーバーは無視してよいが、あれば原本に残る。

### 2.3 status(上り:端末の状態)

```json
{"v":1,"type":"status","src":"dev-001","seq":43,"ts":1791849630,"battery":80,"glass":true}
```

- 一定間隔で送る(30秒ごと【案】)。`battery` は電池の残り(%)。測れなければ項目ごと省く。`glass` はグラスと BLE でつながっているか。
- 【案】GPS が使えれば `lat`・`lon`(10進の度)を付ける(FA-16、できれば)。無ければ省く。
- `online` はふだん省く。切れたときだけ、ブローカーが `false` を流す(§1 の遺言)。

【修正案】LoRa 状態の端末は status を Wi-Fi で送れないため、LoRa に「心拍」(5分おき)を足し、出口が status の JSON に直して送る。電池の残りが載る:

```json
{"v":1,"type":"status","src":"dev-001","seq":43,"ts":1791849630,"battery":80,"via":"lora"}
```

> [!WARNING]
> この形の項目名 `via` は、修正案の「`via = lora`」という記述から書いた。**項目名は共通仕様の更新を待つ。** サーバーは、`glass` や `via` が無くても受け付ける。

### 2.4 ack(上り:届いた確認)

現行のたたき台:

```json
{"v":1,"type":"ack","src":"dev-001","seq":44,"ts":1791849601,"ack_src":"pc","ack_seq":7}
```

【修正案】seq が 0 に戻って特定できなくなる問題を避けるため、`ack_mid` で返す:

```json
{"v":1,"type":"ack","src":"dev-001","seq":44,"ts":1791849601,"ack_mid":12}
```

- 意味:`src` の端末が、`mid=12` の text を受け取った。
- 範囲:【修正案】v1 は「端末に届いた」まで(グラスに表示した、本人が確認した、は出さない)。

**修正案の合意前の暫定**

| 届いた ack | 対応づけ |
|---|---|
| `ack_mid` がある | `messages.id` に直接 |
| `ack_src="pc"` と `ack_seq` だけ | 同じ seq の直近(10分など)の messages に対応づける |
| 曖昧 | 対応づけず、原本(events)に残す |

### 2.5 定型信号コード・指示コード・ポジション番号

10/20 の決定で、定型信号は4種類に限らず**最大31種類**になった。一覧は段階0で `共通仕様/01` に書く(未決)。

| 番号 | 範囲 | 例 | 一覧を持つところ |
|---|---|---|---|
| 定型信号 `code` | 1〜31 | 1=SOS(10/13 のたたき台)、了解、到着、応援を頼む、無事 | 共通仕様。サーバーは数値のまま保存し、名前は画面側 |
| 指示コード `icode` | 【案】1〜255 | 移動、集合、退避 | 【案】サーバーの指示コード表(`instruction_codes`)。共通仕様にも同じ一覧を書く |
| ポジション `pos` | 【案】0〜255(0=場所なし) | 3=北口 | サーバーのポジション表(`positions`)。名前と場所は W8 で変えられる |

- **SOS は `code = 1` のまま**とした(SOS の知らせ・並び順がこの値を使う)。共通仕様で変わったら合わせる。
- 未定義のコード・ポジションも保存する(表に無い番号は、画面で番号のまま出す)。
- 範囲の【案】は、LoRa のパケット(`共通仕様/05`)で 1 バイトを想定した値。パケットの形が決まったら合わせる。

### 2.6 本部に届いた(サーバー → 端末)【案】

10/20 の決定で、端末のグラスの表示が「送った → 近くに届いた → **本部に届いた**」と進む(D-09、FB-05)。SOS は届くまで送り直す(FA-03)。そのため、サーバーが signal を受けたことを端末に返す。

```json
{"v":1,"type":"ack","src":"pc","seq":9,"ts":1791849601,"ack_src":"dev-001","ack_seq":42}
```

| 項目 | 内容 |
|---|---|
| トピック | `reray/v1/down/{id}/ack`(`{id}` は signal を送った端末) |
| `ack_src`・`ack_seq` | 受けた signal の `src` と `seq` |
| いつ返すか | signal を保存したあと。**重複で捨てた signal にも返す**(端末が送り直しを止められるように) |
| LoRa 状態の端末 | 出口が LoRa の ack(type=2)に直して下ろす想定。要合意(§8) |

- 端末の seq は起動時に乱数から始まり、10分の窓で同じ組は出ない前提(【修正案】#3)なので、`ack_seq` で特定できる。

## 3. 検証の規則(サーバーの受信側)

| 条件 | 扱い |
|---|---|
| JSON として読めない | 原本のみ保存して捨てる。警告ログ |
| `v` が 1 でない | 原本のみ保存して捨てる |
| `type` がトピックの末尾と一致しない | 原本のみ保存して捨てる |
| `src` が `dev-NNN` 形式でない、またはトピックの `{id}` と違う | 原本のみ保存して捨てる |
| 端末ID の数値が 0 または 65535 以上 | 捨てる(0=サーバー、65535=全員は端末に割り当てない) |
| `seq` が 0〜65535 でない | 原本のみ保存して捨てる |
| 本文が大きすぎる(目安 4 KB 超) | 原本のみ保存(切り詰め)して捨てる |
| 登録されていない端末の signal / status | **保存する**。`registered = 0` で端末の表に作り、画面で分かるようにする |
| 未知の項目がある | 無視して受け付ける(原本には残る) |

## 4. HTTP API

JSON、UTF-8。パスの接頭辞は `/api`。検証版は認証なし(ローカル LAN のみ)。

### 4.1 チーム案の API(`サーバーサイド/01_API`)

| 方法 | パス | すること | 使う画面 |
|---|---|---|---|
| GET | `/api/devices` | 全端末と今の状態を返す | W2 |
| GET | `/api/devices/{id}` | 1台の状態を返す | W3 |
| POST | `/api/devices` | 端末を登録する | W6 |
| PUT | `/api/devices/{id}` | 持ち主の名前を変える | W6 |
| POST | `/api/messages` | 文字を送る | W3、W4 |
| GET | `/api/messages/{id}` | 1通が何台に届いたかを返す | W4 |
| GET | `/api/logs` | 記録を返す。端末、種類、日付でしぼれる | W3、W5 |

#### 端末の一覧(`GET /api/devices`)

```json
[
  {
    "id": "dev-001",
    "owner": "山田",
    "online": true,
    "via": "wifi",
    "battery": 80,
    "glass": true,
    "position": {"no": 3, "name": "北口"},
    "last_signal": {"code": 2, "pos": 3, "at": "2026-10-13T15:00:00+09:00"}
  }
]
```

- `online`:サーバーが判定した値(`ARCHITECTURE_2026-10-22.md` §5)。`via`:最後に届いた経路。`battery`:空もありうる。
- `position`【案】:最後に届いた signal の `pos` と、ポジション表の名前(W2 のポジション列)。名前が無ければ `name` は空。
- 登録されていない端末は、`owner` が空で `registered: false` を付ける【追加案】。
- 時刻は ISO 8601。画面の表示は日本時間(+09:00)。

#### 文字を送る(`POST /api/messages`)

```json
{"dst": "all", "body": "北口に集合してください"}
```

【案】指示コードの形(W3 で LoRa 中の端末に送るとき、FW-06):

```json
{"dst": "dev-001", "icode": 1, "pos": 3}
```

`body` と、`icode`+`pos` のどちらか一方を送る。指示コードの形なら、サーバーが指示コード表とポジション表から `body` を作る。

返すのは、DB に付けた番号:

```json
{"id": 12}
```

| 項目 | 内容 |
|---|---|
| `dst` | 端末ID か `all`。登録されていない端末ID は 422 |
| `body` | 上限を超えたら 422(§2.1) |
| `icode`・`pos` | 【案】表に無い `icode` は 422。`pos` は表に無くても送れる(番号のまま) |
| 順序 | サーバーは seq を付けて **DB に保存してから** MQTT の `reray/v1/down/...` へ流す |
| `id` | 【修正案】text の `mid` になる |
| 失敗 | MQTT に流せなかったら 503。保存した行は残し、`failed` として記録する【追加案】 |

#### 1通の届き具合(`GET /api/messages/{id}`)【案】

```json
{
  "id": 12,
  "dst": "all",
  "body": "北口に集合してください",
  "sent_at": "2026-10-16T15:00:00+09:00",
  "wifi": {"total": 5, "acked": 4},
  "lora": {"total": 1, "acked": 0},
  "devices": [
    {"id": "dev-001", "owner": "山田", "via_at_send": "wifi", "acked_at": "2026-10-16T15:00:03+09:00"},
    {"id": "dev-006", "owner": "鈴木", "via_at_send": "lora", "acked_at": null}
  ]
}
```

- **自由な文**:LoRa 状態の端末には届かない(Wi-Fi に戻れば、溜めた text が届く)。**分母は「送った時に Wi-Fi だった端末」**とし、LoRa 状態の端末は別に数える。
  画面の表示例:`5台中4台に届いた(LoRa中: 1台 → つながり次第届きます)`
- 【案】**指示コードの形**:10/20 の決定で LoRa でも下ろすため、LoRa 状態の端末も分母に入れる。`wifi` / `lora` の内訳は同じ形で返す。LoRa の端末からの「届いた」がサーバーまで戻るかは未決(§8)。
- `via_at_send` は送信時に端末の表から記録する(`DATA_MODEL_2026-10-22.md` の `message_targets`)。**あとで状態が変わっても、当時の分母が残る。**
- LoRa 状態の端末があとで Wi-Fi に戻って ack を返したら、`acked_at` が入る(分母は変えない)。

#### 記録(`GET /api/logs`)

| 絞り込み | 内容 |
|---|---|
| `device` | 端末ID |
| `type` | `text` / `signal` / `ack` / `status` / `transcript`【案】 |
| `from`、`to` | 日付・時刻の範囲 |
| `limit`、`before` | 件数とページング【追加案】 |

返す項目は、画面 W5 の項目(時刻、種類、だれから、だれへ、中身、経路)に合わせる(`web/02_画面の項目`)。時刻はサーバーの受信時刻。

### 4.3 ポジション・指示コード・文字起こし【案】

10/20 の決定で増えた API。`サーバーサイド/01_API` に足すまで【案】。

#### ポジション表(`/api/positions`、W8)

```json
[{"no": 3, "name": "北口", "place": "正面玄関の外", "updated_at": "2026-10-22T10:00:00+09:00"}]
```

| 方法 | パス | 送る項目 | 返す |
|---|---|---|---|
| GET | `/api/positions` | — | 全件 |
| POST | `/api/positions` | `no`(◎)、`name`(◎)、`place` | 作った1件。`no` が重複なら 422 |
| PUT | `/api/positions/{no}` | `name`、`place` | 変えた1件 |
| DELETE | `/api/positions/{no}` | — | 204。過去の記録の `pos` は番号のまま残る |

#### 指示コード表(`/api/instruction-codes`)

```json
[{"code": 1, "text": "へ移動"}, {"code": 2, "text": "に集合"}, {"code": 3, "text": "から退避"}]
```

| 方法 | パス | 送る項目 |
|---|---|---|
| GET | `/api/instruction-codes` | — |
| POST | `/api/instruction-codes` | `code`(◎)、`text`(◎) |
| PUT | `/api/instruction-codes/{code}` | `text` |

- 文は「ポジション名 + `text`」で作る(例:`北口` + `へ移動`)。ポジションが無い(`pos = 0`)ときの文の作り方は要合意。
- 指示コードは端末とも共有する番号なので、**変えるときは共通仕様を先に直す**。DELETE は作らない。

#### 文字起こし(`POST /api/transcripts`、FS-08)

```json
{"dst": "all", "body": "北口に集合してください", "speaker": "本部"}
```

| 項目 | 必須 | 内容 |
|---|---|---|
| `dst` | ◎ | 端末ID か `all` |
| `body` | ◎ | 文字にした文。上限は text と同じ(長ければ 422。分けるのはアプリ側) |
| `speaker` | △ | 話した人(記録用) |

- サーバーは `transcripts` に記録し、自由な文として `messages` を作って配る(`POST /api/messages` と同じ流れ)。返すのは `{"id": 14, "transcript_id": 5}`(`id` は messages.id)。
- 入口を API にするか MQTT にするかは、共通仕様 03 で未決。ここでは API の案とした(認証・検証を1か所にまとめられるため)。
- これは**災害用**(アプリで文字にして送る)の入口。**普段用**(音声を MQTT で受けてサーバーで文字にする)は【将来】で、トピックの案は `ARCHITECTURE_2026-10-22.md` §12.1。

### 4.4 エラーの形

```json
{"error":"unknown_device","message":"dev-099 は登録されていません"}
```

| コード | 意味 |
|---|---|
| 400 | 形式の誤り |
| 404 | 存在しない |
| 422 | 内容の誤り |
| 503 | MQTT に接続できない |

## 7. ハード試作(`tkitora/re-ray`)との差

ハード側の試作は、チームの仕様と違う案を持っている。**チーム仕様が正**なので、サーバーはチーム仕様に合わせて作る。つなぐときに食い違いを探すための一覧。

| 項目 | チーム仕様 | ハード試作 | サーバーへの影響 |
|---|---|---|---|
| LoRa のパケット | 10バイト | 17バイト前後 + 署名 4 バイト(5種類) | なし(出口が JSON に直す) |
| signal の追加項目 | なし | `x`(区域、人数区分、GPS、RSSI、SNR) | 無視してよい。あれば原本に残る |
| 区域 | なし(地図も出さない) | 端末番号と区域の対応表 | **区域は扱わない**。必要になったら端末の表に任意の列を足す(`DATA_MODEL_2026-10-22.md` §5) |
| 下りの text を LoRa で運ぶか | **10/20 に決定**:自由な文は運ばない。指示コード+ポジションは運ぶ | 自由な文字は載らない(18 バイト)。定型の指示コード表を推奨 | 指示コードの形で `icode`・`pos` を付ける(§2.1) |
| MQTT の ack | `ack_src` と `ack_seq`、【修正案】`ack_mid` | `ack_src`(指示の送信元)と `ack_seq`。LoRa の「近傍に届いた」「サーバー到達」は MQTT に出さない | `ack_mid` が合意されたら、出口への反映が要る |
| seq の始まり | 0 から。【修正案】起動時に乱数 | 電源を切ると 0 に戻る可能性 | 【修正案】が合意されれば、重複判定の窓(10分)で足りる |
| 重複の判定 | サーバー:直近10分の `src` と `seq`【案】 | 出口・端末:`(src, seq, type)` を直近 50 件 | 役割が違う。出口側はループ防止、サーバーは最終判定【修正案】 |
| ブローカーの設定 | 未決 | 検証用に匿名・永続化なし | このリポジトリは永続化あり(`config/mosquitto.conf`) |

## 8. 10/20 の決定で、共通仕様に足してほしいこと

サーバーは下の【案】で作り始める。共通仕様(`02_メッセージ形式`・`03_MQTTトピック`・`05_LoRa`)で決まったら、ここを直す。

| # | 内容 | サーバーの案 | 決めるところ |
|---|---|---|---|
| 1 | signal のポジション番号の項目名と範囲 | `pos`、0〜255(0=場所なし) | 共通仕様 01・02 |
| 2 | 指示コードの下りの形 | `type = text` のまま `icode`・`pos` を足す。`body` に文も入れる | 共通仕様 02 |
| 3 | LoRa 状態の端末へ指示を下ろす経路 | 未案。出口がどのトピックを購読し、どの端末宛てを LoRa に流すか。サーバーは端末ごとの `via` を知っているので、LoRa 宛てだけ別のトピックに出す形もありうる | 共通仕様 03・05 |
| 4 | 本部に届いた(サーバー → 端末の ack) | `down/{id}/ack` に `ack_src`・`ack_seq`(§2.6) | 共通仕様 02・03 |
| 5 | LoRa の端末からの「指示が届いた」をサーバーまで戻すか | 戻すなら、LoRa のパケットに `mid` が載らないので、出口が `ack_seq` から `mid` を引けるようにする必要がある | 共通仕様 05 |
| 6 | 文字起こしの入口 | `POST /api/transcripts`(§4.3) | 共通仕様 03 |
| 7 | status の GPS の項目名 | `lat`・`lon` | 共通仕様 02 |
| 8 | 定型信号・指示コード・ポジション番号の一覧 | SOS は `code = 1` のまま | 共通仕様 01(段階0の宿題) |
